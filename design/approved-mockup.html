Case study [2026] · Work in progress · All data is fictional

AI agents draft a fund’s reporting calendar. A human specialist approves every rule.

Investment funds must send regular reports to government regulators, each by a deadline set in law. My tool uses AI to read those laws and draft the deadlines, quoting the exact sentence each one comes from. A human compliance specialist checks and approves the work at three points, and plain code works out the final dates.

The short version

  1. [1]Today a compliance specialist reads the law and types every reporting deadline into a spreadsheet by hand. Mistakes slip in: two of the team’s own documents give the same monthly report different lead times, 3 days and 10 days.
  2. [2]In my tool, AI agents do the first reading of the law. Every rule they pull out must quote the exact sentence it came from, and a second AI agent checks that the quote is real.
  3. [3]A human specialist then approves each rule, one at a time, at three checkpoints. There is no “approve all” button, and nothing is approved by default.
  4. [4]The deadlines themselves are worked out by ordinary code, not by AI, so the same input always gives the same date.
  5. [5]Before building anything, I wrote an answer key: the exact results the tool should produce, down to all 22 deadlines. Every test run will be marked against it.

How it is built

One designer, two crews of AI agents

The development crew helps me build. It is ten AI agents, each set up to play one role on a product team, such as architect, engineer or tester. They follow a method called AI-Assisted Multi-Agent Application Development. I brief each one, review its work and make the decisions it isn’t allowed to make.

The application crew lives inside the product. These are the AI agents that read the law, check the quotes and suggest which rules apply to the fund. They are planned to run on CrewAI, a tool for running teams of AI agents.

1.1Who it affects

Two people use the product. A third group sends most of the reports but doesn’t use it yet.

[!]Early profiles, based on project documents. Nobody has been interviewed yet.

Compliance specialist

The main user. Owns the fund’s deadline calendar.

Reads every new set of rules, works out what each one requires, sets deadlines by hand and chases the outside firms that send the reports.

Needs

  • See exactly where each rule comes from, so it can be checked quickly.
  • Have disagreements between sources caught by a check, not by luck.
  • Nothing important happens without their approval.
  • Deadlines worked out the same way every time.

Fund manager

Only reads the finished calendar.

Responsible for the reports being sent, but sends few of them personally. Today they get a long legal document. Managers based outside Luxembourg know the local rules least well.

Needs

  • Know what is due and when, without reading legal text.
  • Understand why each report applies to their fund.
  • Know who sends each report, so they know whether they need to act.
  • See only information a specialist has approved.
Outside firms that send the reports

Each deadline names who sends it. They don’t use the product yet.

1.4Why the answers drift

One fund has to follow several sets of rules at once: Luxembourg law, EU law, tax rules, and the rules of each country where it is sold. Each set has its own regulator, deadlines and wording, so the same report can be described differently in different places. The project’s test data covers several of these layers.

2.1The four records

The product keeps four kinds of record. Each one keeps the same ID every time the tool runs, so any date on the calendar can be traced back to the sentence of law it came from.

Tracking whether a report has been sent is out of scope for now. Because each deadline keeps its ID, that can be added later without rebuilding the calendar.

    Design question · Planning phase

    Question
    Could a rejected rule sneak back onto the calendar without anyone deciding it should?
    What I found
    When I mapped every way a rule could come back, editing a rejected rule turned out to be a second way in, with no reason asked for.
    What changed
    Rejected rules are now locked. To change one, the specialist has to reopen it and give a reason, and it goes through checkpoints 1 and 2 again.

    2.4When “not sure” is right

    Sometimes the honest answer is “not sure”. The fictional fund is sold in Spain, but nobody has confirmed it is registered with the Spanish regulator. The Spanish report is only required for registered funds, so the right answer is “not sure”, and a person decides. An AI that answers “yes, it applies” sounds reasonable but is wrong.

    OBL-04 · Quarterly report for SpainNot sure · a person decides

    This report is only required if the fund is registered with the Spanish regulator. Being sold in Spain isn’t the same thing, and the fund’s records don’t confirm registration.

    2.5Dates come from code

    Month ends, leap years and weekends are easy to get wrong, so no AI sets a date. Plain code takes a starting date, adds the time allowed, then applies that report’s own weekend rule. Some deadlines move to the next working day when they land on a weekend. Tax deadlines stay where they fall.
